二、跨模型审查：路线批准 + 四项约束
════════════════════════════════════════════

**路线**：批准由 **agy** 承担审查。理由：跨模型审查的价值在于**第三方独立**；WorkBuddy
同时是审计方与代码复核方，若再由 WorkBuddy 兼作"审查方"，两个角色塌缩为同一个主体，
独立性不成立。故审查必须由 WorkBuddy 之外的模型出具。

**约束（四项，缺一即审查不被接受）**

1. **逐字留痕**：`docs/review-log.md` 必须包含
   - 送审**提示词原文**（verbatim，不得转述、不得"整理"）；
   - 审查模型**回复原文**（verbatim；若过长，可另存 `docs/review-log-appendix.md`，
     但 review-log 必须给出文件路径与 SHA256）；
   - 审查方身份：**提供方 / 模型名 / 调用方式**，并同时声明**实现方**（写 snr.py / lsig.py
     的模型与提供方）。"与实现方不同"须可核验，不得只写"已由另一模型审查"。
   - openclaw 不得对回复做摘要式过滤后只留结论；分歧与不确定表述必须原样保留。

2. **对抗式提问**：提示词必须要求审查方**主动找错**，而非确认正确。至少包含：
   - "下列实现是否在任一处与给定规格不符？逐条指出；若无，说明你检查了哪些边界。"
   - "是否存在期望值由被测代码自算（自证）的风险？"
   - "除零、非有限输入、掩码轴向、取整语义四处，分别指出可能的错误实现方式。"
   - "给出你认为最可能失败的一个输入场景。"
   禁止的提示方式："请确认该实现正确""请审查并确认无误"。

3. **最小披露（脱敏）**：只发送**代码文件 + 规格相关段落**（协议第四节相关文字、
   n_T 取整规则、期望值规则）。**禁止外发**：预算台账、api-ledger、execution-log、
   用户身份信息、含本机用户名的绝对路径（发送前替换为相对路径或占位符）。
   本仓库代码最终会公开发布，故代码本身无保密问题；但项目策略与个人路径不外发。

4. **成本留痕**：若调用产生现金费用，逐笔记入 `docs/api-ledger.csv`（累计不得超 10 USD）；
   使用免费额度则注明"免费额度，无现金支出"。

**验收标准（WorkBuddy 审计时执行）**：提示词是否为对抗式（非确认式）；回复是否逐字在案；
实现方/审查方身份是否可核验且不同；审查是否触及除零/非有限/轴向/取整四处中的每一处；
对每条分歧是否给出处置（采纳 / 不采纳 + 理由）。
**空泛意见（如"实现看起来正确"）判定为审查不通过，须重审。**
